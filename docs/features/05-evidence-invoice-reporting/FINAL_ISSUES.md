| F05-FINAL-001 | **P0** | **Restricted export data can be recovered with only generic export authority.** Request creation correctly requires `reportPermission(definition.id())` at `FinanceGovernanceService.java:691-694`. In contrast, `exportStatus` requires only `finance.read` at `:734-756`; `replayExport` requires only `report.export` at `:759-795`; and `exportDownload` requires only `report.export` at `:798-839`. `PAYMENT_AGING`, `EXCEPTION_REOPEN` and `COMMUNICATION_AUDIT` use more restrictive permissions when queued. A same-engagement user who has generic `report.export`/`finance.read` but lacks the report's permission can therefore use a known export UUID to read its metadata, replay it, and download its restricted rendered content. UUID entropy is not an authorization boundary. This violates requirements 12/13/14 and `T-REP-004`, `T-F05-SEC-001/002`. | Load the export header before status, download and replay; require both generic export access where appropriate **and** the stored report code's current `reportPermission`. Apply the same check to every export detail/download/replay route and audit the denied attempt. Do not authorize solely by `requested_by_subject` or UUID secrecy. | MockMvc: a Finance/Vendor actor with `finance.read`/`report.export` but without `payment.update` and `finance.audit.read` receives the same safe 403/404 for another actor's `PAYMENT_AGING`/`COMMUNICATION_AUDIT` status, download and replay UUID. Authorized Finance/audit actor succeeds. Verify no private artifact bytes, filters or job state leak and denial emits a security/audit event. |
| F05-FINAL-002 | **P0** | **Exact invoice/package lineage is not enforced.** Package generation calls `currentInvoiceArtifact(monthId)` (`FinancePackageService.java:85-102`), whose query selects any non-superseded/non-cancelled invoice for the month ordered by `invoice.updated_at` (`:686-716`). Readiness later obtains `currentPackage(invoice.monthId())` with no invoice/document/artifact linkage (`FinanceInvoiceService.java:561-577`, `:1163-1179`). `PACKAGE_MANIFEST` then passes solely because that month package is `CURRENT` (`:1194-1224`). Consequently, after a primary invoice A and a newer credit/debit/correction document B exist, package generation can embed B while readiness/submission of A accepts that package as A's exact lineage. This contradicts requirements 10 §§3/5/6/7, F05 tasks 007–010 and `T-INV-005`, `T-PROC-002/003`. | Model and persist the exact invoice ID, invoice document version and artifact hash/ID on a package (or make packages invoice-version scoped). Require them to equal the invoice/readiness input during readiness, submit, review, exception and payment approval. Treat a changed invoice version/note as a new package lineage and disclose appropriate related-note attachments rather than silently substituting the invoice copy. Add database scope/foreign-key/trigger protection where feasible. | Integration flow: create primary A, generate package A, create/upload credit note B, generate package B, then attempt readiness/submit/review/payment for A using package B. It must fail with a typed exact-lineage conflict; A succeeds only with package containing A's current document hash/version. Repeat for correction/replacement and stale/superseded package paths. |
| F05-FINAL-003 | **P1** | **Exception duration and two-person approval are not enforced operationally.** `acceptException` checks `validUntil` only when created (`FinanceGovernanceService.java:386-411`), then creates an eligible `EXCEPTION_ACCEPTED_BY_PROCUREMENT` run (`:1289-1359`). `FinanceInvoiceService.submit` allows that run with no query that the linked exception remains unexpired (`:697-735`). The read model merely labels it `EXPIRED` (`FinanceInvoiceService.java:1060-1088`), so an expired exception can still submit/advance. Also, a policy requiring a second approval only validates a caller-provided `secondApproverId` has permission (`FinanceGovernanceService.java:404-411`); no authenticated action, authority snapshot or audit is produced by that second subject. This violates requirement 10 §6 and `T-PROC-003/005`. | Represent approval as its own immutable, authenticated action (or a pending state) and require a distinct second subject to approve with scoped authority before the exception becomes eligible. Bind both approvals to invoice/package/readiness/rule/policy/version. Enforce `valid_until` in submit/review/payment gates and implement an idempotent expiry worker or on-read/write transition that invalidates/reblocks the current exception run with audit/outbox. Reject re-accepting an already accepted rule without a governed new exception/review. | Clock-controlled tests: primary approver cannot self-nominate a second approver; a mere identifier does not activate the exception; only the authenticated distinct authorized second actor activates it. After `valid_until`, submit/review/payment are denied, current readiness is ineligible/stale, and exactly one expiry audit/outbox event exists. Cross-tenant, revoked and expired second approvers are denied. |
| F05-FINAL-004 | **P1** | **XLSX package bytes are not deterministic.** Package generation renders XLSX (`FinancePackageService.java:166-175`). `LocalFinanceReportRenderer.xlsx` writes fresh `ZipEntry` values without setting a fixed timestamp (`LocalFinanceReportRenderer.java:85-149`, especially `entry` at `:224-229`), so the ZIP/XLSX container records generation-time metadata. Identical logical inputs rendered in different ZIP timestamp windows yield different bytes/hashes. This violates requirements 10 §5.4, F05 task 005/007 and `T-PKG-003`. PDF export metadata iteration also uses an unordered input map for normal report exports (`FinanceOperationsWorker.java:170-182`, renderer `:160-170`), so deterministic ordering should be made explicit there too. | Set every ZIP entry timestamp/extra fields deterministically (for example a documented epoch), use a stable entry order, and use ordered/canonical metadata and row/column ordering before rendering all formats. Record renderer/schema version and use byte-hash equality as the contract. | Unit test renders identical package/report inputs before and after a timestamp boundary and asserts byte-for-byte equal JSON/PDF/CSV/XLSX output and equal SHA-256. A changed ordered source/policy/render version must change the expected output/hash only. |
| F05-FINAL-005 | **P1** | **Most F05 collections still violate the cursor/no-unbounded-select contract.** Only control tower and export history use `FinancePageCursorCodec`. `FinanceController.page` slices a fully materialized service list and encodes raw Base64 `key:<id>` cursors (`FinanceController.java:491-558`). Those cursors are unsigned, unbound to route/actor/scope and have no expiry; services query all scoped rows before the controller discards all but 50. This violates requirements 13/16/22, F05 task 016 and `T-F05-API-001`, `T-F05-PERF-001`. | Replace generic paging with per-resource repository keyset queries using the existing signed cursor codec (or a shared typed keyset abstraction). Bind every cursor to resource, subject, authorized scope and a clearly documented snapshot policy; fetch at most page-size-plus-one rows and count only when required. Remove the generic Base64 cursor path. | HTTP/integration tests for each paged F05 endpoint prove tamper/cross-route/cross-user/expired rejection, page-size bounded SQL, no duplicate/skip across concurrent inserts and safe scope changes. Add an explain/large-fixture check showing no full history materialization. |
| F05-FINAL-006 | **P1** | **Playwright does not exercise the deployed Java/PostgreSQL contract.** `e2e/finance.spec.ts` installs `mockFinanceApi` for every journey, and `playwright.config.ts` starts Vite with `VITE_BACKEND_DEV_URL=http://127.0.0.1:9`. | F05-FINAL-007 | **P2** | **The canonical package manifest omits required artifact metadata.** `completeManifestItems` writes only logical/source IDs, version/hash/provenance/timestamps and optional artifact ID (`FinancePackageService.java:719-815`). It omits the invoice artifact safe name, MIME type, byte size, object version, classification and retention class even though `InvoiceArtifact` supplies them (`:686-710`). `packageView.items` later reconstructs those fields by joining the artifact table (`:599-647`), so the JSON manifest output/hash itself is incomplete. | F05-FINAL-008 | **P2** | **Control-tower snapshot is insert-stable, not value-snapshot stable.** The query bounds only `engagement_months.created_at <= snapshotAt` while deriving package/invoice/readiness/payment values from the live `f05_control_tower` view (`FinanceGovernanceService.java:78-130`).
