# F04 Independent Code Analysis Issues

**Disposition:** every finding is **Open**. P1 items are local G1/G2 blockers; P2 items are important debt to resolve before production-scale use. Existing F04 issue IDs are cross-referenced rather than duplicated.

## P1 -- local release blockers

### F04-ANL-001 -- A project-scoped reader can disclose the whole month confirmation record

- **Evidence:** `requireMonthRead` accepts a principal with any project-scoped `certification.read` permission and returns a `Scope` at [CertificationAuthorizationService.java](../../../backend/src/main/java/com/vms/workflow/security/CertificationAuthorizationService.java#L40-L53). `requireRequestRead` discards that scope and merely invokes it at [CertificationAuthorizationService.java](../../../backend/src/main/java/com/vms/workflow/security/CertificationAuthorizationService.java#L135-L138). `BusinessConfirmationService.request` then returns the unfiltered `requestView` at [BusinessConfirmationService.java](../../../backend/src/main/java/com/vms/workflow/application/BusinessConfirmationService.java#L228-L231), including all recipient displays, all actions/comments, notification history, and all request lineage at lines 419--442. The browser renders those fields directly at [confirmation.requests.$requestId.tsx](../../../src/routes/confirmation.requests.$requestId.tsx#L89-L137).
- **Impact:** Someone scoped to Project A can obtain a known Project B/month request ID and disclose cross-project recipient email/display data, action comments, notification metadata, confirmation lineage, and exact source references. The workspace's project filtering does not protect this direct route.
- **Fix:** Resolve and retain the request's project/scope manifest in authorization. Either require engagement-wide read for the unredacted request or return only the caller's eligible project contribution and a redacted aggregate. Add HTTP tests for known-ID cross-project read, engagement-wide read, and a multi-project eligible confirmer.
- **Disposition:** Open -- G2 local blocker. Distinct from `F04-BE-004`, which concerns action authority rather than read disclosure.

### F04-ANL-002 -- `PROJECT_SPECIFIC` quorum is unrepresentable for an owner assigned to multiple projects

- **Evidence:** Request creation produces one eligibility row per `(subject, project)` at [BusinessConfirmationService.java](../../../backend/src/main/java/com/vms/workflow/application/BusinessConfirmationService.java#L572-L595) and [V11](../../../backend/src/main/resources/db/migration/V11__certification_confirmation_local.sql#L419-L428). The action API accepts no project selector, and `eligibility` deterministically selects only the first matching row (`ORDER BY sequence_number LIMIT 1`) at [BusinessConfirmationService.java](../../../backend/src/main/java/com/vms/workflow/application/BusinessConfirmationService.java#L716-L737). Yet `PROJECT_SPECIFIC` completes only after actions cover every distinct project at lines 756--780. The TypeScript action request likewise has no project field at [contracts.ts](../../../src/features/certification/contracts.ts#L407-L411).
- **Impact:** If the same eligible product owner is assigned to Project A and Project B, one authenticated action is recorded only for the first project while the quorum requires both. A second action cannot select the other project; the request remains `AWAITING_RESPONSE` forever. This violates the required project-specific quorum path in `T-CONF-008`.
- **Fix:** Make the project contribution explicit and authorize it against the eligible row (for example a selected project ID or a server-calculated set of covered projects), with one unique action/contribution per request/project. Alternatively define and implement a captured policy that one eligible owner affirmatively covers all of their listed projects. Add committed concurrent tests for shared owners, duplicate contributions, and mixed project scopes.
- **Disposition:** Open -- G2 local blocker.

### F04-ANL-003 -- Mixed multi-party decisions silently select a terminal outcome instead of entering governance conflict

- **Evidence:** After each action, a correction or rejection unconditionally becomes `CHANGES_REQUESTED` or `REJECTED`; only confirmations wait for quorum at [BusinessConfirmationService.java](../../../backend/src/main/java/com/vms/workflow/application/BusinessConfirmationService.java#L327-L341). The action is then recorded and an invalidation inserted without conflict detection or governance work at lines 349--376. V11 permits no conflict-review request state ([V11](../../../backend/src/main/resources/db/migration/V11__certification_confirmation_local.sql#L379-L413)), although the TypeScript contract already includes `CONFLICT_REVIEW` at [contracts.ts](../../../src/features/certification/contracts.ts#L28-L40).
- **Impact:** In `ALL`, `N_OF_M`, ordered, or project-specific quorum, a prior confirmation followed by another eligible party's reject/correction is converted into a terminal result based on the latter action. The conflicting evidence is not represented as a blocked governance decision, and no governance task exists. This contradicts `T-CONF-008` and F04-TASK-014/-016.
- **Fix:** Add an explicit `CONFLICT_REVIEW`/governance state and immutable conflict/work-item fact; transition atomically when incompatible contributions exist, stop normal quorum counting, and require a separately authorized resolution/superseding request. Update Java and TypeScript state unions together, then test every quorum mode with committed competing actions.
- **Disposition:** Open -- G2 local blocker.

### F04-ANL-004 -- Evidence lineage loses criterion ownership and is not database-scope-enforced

- **Evidence:** V11's `delivery_evidence_items` stores only `outcome_id` or `clarification_id` plus `artifact_id`; it has no `criterion_id`, unique `(outcome_id, artifact_id)`, or insert/update source-scope trigger ([V11](../../../backend/src/main/resources/db/migration/V11__certification_confirmation_local.sql#L171-L188), 791--895, 1147--1152). The service receives `criterion.evidenceReferenceIds` but persists each through an `outcomeId`-only method at [CertificationWorkflowService.java](../../../backend/src/main/java/com/vms/workflow/application/CertificationWorkflowService.java#L1057-L1074); its service-only check is at lines 1078--1104. The read model returns empty criterion evidence lists at lines 835--844 and returns all linked evidence only at the outcome level at lines 846--862.
- **Impact:** A database writer/future service can attach a cross-engagement or cross-month artifact to an outcome because the foreign key proves only artifact existence. In normal service use, evidence supplied for a criterion loses that association on persistence/readback; repeating the same artifact in criterion and outcome lists creates duplicate evidence rows and changes signed manifests. Reviewers cannot prove which mandatory criterion was evidenced.
- **Fix:** Model an immutable evidence association with exactly one parent kind and, for submission evidence, an optional/required criterion FK that is checked against the outcome's deliverable. Add a unique key for the intended association and a trigger/composite scope check from artifact through outcome/clarification to month/engagement. Batch-read criterion-specific evidence and add direct-SQL cross-tenant/month, duplicate, and criterion-readback tests.
- **Disposition:** Open -- G1 local blocker. `F04-BE-009` remains the separate missing evidence-*policy* enforcement finding; this is the missing storage/invariant and lineage model.

### F04-ANL-005 -- The production month DTO never supplies the confirmation preview required to create a request

- **Evidence:** `MonthCertificationView` includes `confirmationPreview` at [CertificationDtos.java](../../../backend/src/main/java/com/vms/workflow/api/CertificationDtos.java#L339-L359), but `workspaceView` unconditionally passes `null` in that position at [CertificationWorkflowService.java](../../../backend/src/main/java/com/vms/workflow/application/CertificationWorkflowService.java#L665-L689). The React governance page renders the due input and create/queue button only inside `if (preview)` at [confirmation.$monthId.tsx](../../../src/routes/confirmation.$monthId.tsx#L180-L275); otherwise it renders only “No request preview available.” The Playwright fixture invents a populated preview at [certification-api.ts](../../../e2e/fixtures/certification-api.ts#L246-L257).
- **Impact:** A real Java-backed ready month has no interactive confirmation-request path despite the controller/service endpoint existing. Browser fixture passes cannot establish `T-F04-UI-004`, because they exercise a response the controller never emits.
- **Fix:** Implement a server-authoritative preview builder from the same locked/captured sources used by request creation, with recipient/eligible/quorum/scope/due details and redaction by caller scope; or expose a dedicated preview endpoint. Return an explicit typed unavailable/blocker state rather than `null` when it cannot be built. Add Spring JSON/HTTP and non-intercepted browser integration coverage.
- **Disposition:** Open -- G2 local blocker. Separate from `F04-FE-009`, whose browser-offset defect becomes relevant once a real preview exists.

### F04-ANL-006 -- Readiness CTAs point at routes the SPA does not provide

- **Evidence:** The readiness service returns `/certification/months/{id}` and `/certification/confirmation-requests/{id}` as CTA paths at [CertificationReadinessService.java](../../../backend/src/main/java/com/vms/workflow/application/CertificationReadinessService.java#L99-L159). React renders each supplied path as an in-app `Link` without mapping it at [components.tsx](../../../src/features/certification/components.tsx#L202-L208). The generated routes are `/certification/$monthId` and `/confirmation/requests/$requestId` ([routeTree.gen.ts](../../../src/routeTree.gen.ts#L263-L315), 477--480), not the server strings. Other returned paths such as `/delivery/integrations` and `/attendance` also do not correspond to the current F01--F03 route names.
- **Impact:** A readiness blocker can name an owner and action but its action link navigates to a dead/non-F04 route, preventing the prescribed corrective journey and hiding the integration defect behind a static browser fixture that substitutes a valid path.
- **Fix:** Treat CTAs as typed route intents (`kind`, parameters) and map them in the client router, or make the API return an agreed frontend route contract. Validate every returned CTA against the route tree in a contract test, including its authorization/redaction behavior.
- **Disposition:** Open -- G2 local blocker.

## P2 -- important hardening and scale debt

### F04-ANL-007 -- Canonical request hashes preserve order for semantically set-like ID collections

- **Evidence:** The canonicalizer sorts map keys but preserves every iterable's received order at [CanonicalEvidenceHasher.java](../../../backend/src/main/java/com/vms/workflow/application/CanonicalEvidenceHasher.java#L54-L88). F04 request DTOs use unordered lists of deliverables, criterion results, evidence IDs, impacted records, and questions (for example [CertificationDtos.java](../../../backend/src/main/java/com/vms/workflow/api/CertificationDtos.java#L23-L53), 78--96, 125--134). Several request hashes pass those records directly to the canonicalizer, including save/summary/reopen at [CertificationWorkflowService.java](../../../backend/src/main/java/com/vms/workflow/application/CertificationWorkflowService.java#L1994-L1998).
- **Impact:** A retained idempotency key retried with the same set of IDs in a different order receives `IDEMPOTENCY_KEY_REUSED` rather than the prior result. Equivalent evidence/criterion sets can also obtain divergent action/request hashes, complicating audit comparison.
- **Fix:** Define ordering semantics per manifest schema: sort set-like lists by stable IDs, retain order only for explicitly ordered values (for example ordered quorum), and normalize Unicode/text if equality is business-semantic. Version manifests when canonicalization changes and add permutation/retry tests.
- **Disposition:** Open.

### F04-ANL-008 -- Workspace hydration has an unbounded per-deliverable JDBC query fan-out

- **Evidence:** `deliverableViews` loads all deliverables then, per deliverable, calls criterion, submission-item, and certification views at [CertificationWorkflowService.java](../../../backend/src/main/java/com/vms/workflow/application/CertificationWorkflowService.java#L692-L728). Submission-item hydration makes additional criterion/evidence queries at lines 753--862; certification hydration makes carry-forward/criterion-result queries at lines 779--878. There is no pagination/limit on the deliverable workspace response.
- **Impact:** A realistic frozen plan produces roughly six or more sequential database queries per deliverable, in addition to timeline/notification queries. Large months cause avoidable latency and connection pressure exactly on review/governance pages.
- **Fix:** Fetch criteria, outcomes, evidence, certifications, carry-forward, and results in bounded bulk queries keyed by the visible deliverable IDs; assemble maps in memory and page/virtualize the workspace. Add a query-count/large-fixture performance test.
- **Disposition:** Open.
